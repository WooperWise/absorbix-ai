1. Проблема и метрики

Проблема. Подбор лекарственной формы, солей, пролекарств и вспомогательных веществ для повышения всасывания — предэкспериментальное решение, которое сегодня опирается на опыт специалиста и разрозненные источники. Один запрос к LLM его не решает: модели путают свойства молекул, придумывают исследования и не различают сильные и слабые доказательства.

Как ставится задача (по ТЗ)

Пользователь — фармаколог или технолог — указывает препарат (МНН, торговое название или структуру) и получает: профиль физико-химических свойств, класс по биофармацевтической классификации (BCS), диагностику ограничивающего фактора всасывания и варианты оптимизации с уровнями доказательности. Результат — гипотезы и обоснования для проверки, а не замена эксперимента.

Метрики успеха (из ТЗ, приняты как целевые)
  • доля известных успешных стратегий оптимизации, воспроизведённых платформой на тестовом наборе;
  • точность диагностики ограничивающего фактора относительно экспертной оценки;
  • доля выводов с проверяемым источником и корректной оценкой доказательности;
  • сравнение с базовой линией (LLM без обвязки) по числу неподтверждённых утверждений;
  • оценка полезности вариантов профильным экспертом.

2. Рынок: как проблему решают сейчас

Разобрано 15+ решений пяти классов: экспертный процесс, цифровая автоматизация (FormulationDE, ADMETlab), механистическое моделирование (GastroPlus, Simcyp, PK-Sim/OSP), интегрированные программы (Certara, Quotient Sciences) и LLM-агенты (ChemCrow). Для каждого — функции, эффективность, схема процесса.

Ключевые выводы сравнения
  • «Самого точного ИИ» без общей задачи не существует: выбор стратегии, прогноз свойства, моделирование экспозиции и подготовка решения — разные рынки с разными критериями.
  • Открытые механистические инструменты (PK-Sim/OSP) дают управляемость и повторяемость, но не заменяют модельные данные конкретного препарата.
  • LLM без инструментов зафиксирована как слабая базовая линия; связка «модель + инструменты + проверяемые источники» — рабочее направление (ChemCrow).
  • Ниша проекта: проверяемое предэкспериментальное решение с уровнями доказательности — не закрыта ни одним из разобранных решений.

3. Архитектура целого решения

Спроектирована архитектура из 19 модулей (M01–M19) с контрактами данных и границами доверия; 10 схем в представлениях C4, 5 JSON Schema и фрагмент OpenAPI. Ключевые решения:

  • Детерминированный каркас с ограниченными LLM-действиями: модель извлекает, формулирует и объясняет; код проверяет, решает и утверждает. Автономность — только после тестов (ADR-05).
  • Наблюдения с провенансом: каждый факт несёт origin_kind (измерение / расчёт / предсказание / суждение) и ссылку на источник; «извлечение LLM» не превращает текст статьи в проверенный факт автоматически.
  • Границы доступа: workspace-изоляция частных данных; секреты и чужие документы не попадают ни в модель, ни в логи.
  • Валидация как отдельный модуль (M19): качество доказывается для конкретной версии и области, а не «вообще».

4. Первая фича: подробный разбор

Вертикальный срез: исследовательский кейс → профиль препарата → диагностика ограничивающего фактора всасывания → до трёх обоснованных кандидатов стратегий → ответ по контракту датасета.

Видение

Фича отвечает на главный вопрос технолога: какие варианты изменения препарата разумно проверить экспериментально, на основании каких данных и при каких ограничениях. Не список советов, а экономика эксперимента: каждый вывод — со ссылкой на факт досье, каждая гипотеза — помечена как гипотеза, численные обещания отсутствуют до появления расчётной модели. Система умеет отказываться: неполное досье → уточняющий вопрос со списком недостающего, а не выдумка.

Почему выбрана первой
  • ядро ценности из ТЗ: профиль и диагностика — первые пункты пользовательского сценария;
  • центр архитектуры: модули M06 (профиль) и M07 (оценка ограничивающих факторов);
  • проверяема формальным оценщиком датасета без новой разметки;
  • изолирована от внешних сетей — работает на фиксированном досье.
Архитектура фичи: шаги, компоненты, данные
кейс (dev-сплит)
 → 1. адаптер кейса: сборка досье            [код]
 → 2. роутер: готов / неполный / вне рамок   [код]
 → 3. извлечение фактов из карточек          [LLM + схема]
 → 4. проверка ссылок fact_refs              [код]
 → 5. профиль + диагноз ограничивающего      [правила + LLM-объяснение]
 → 6. кандидаты ≤3 с опорой на факты         [LLM + схема]
 → 7. сборка ответа, валидация JSON-схемой   [код]

Вход: кейс датасета (намерение, путь введения, требования, текст задачи) + карточки источников с провенансом. Выход: JSON по схеме benchmark_response: статус решения, утверждения со ссылками, предупреждения, недостающие входы, кандидаты. Где модель: только извлечение, формулирование и объяснение — всегда со structured output; решения принимает код. Численные прогнозы: пусто, расчётной модели нет — честная позиция, не уклонение.

Код не написан — задание блока 7 требует детальное описание; реализация — план следующей недели.

6. Хранилище документов (RAG)

Ответ на вопрос «нужен ли RAG» дан по компонентам платформы, а не «вообще»:

  • Первая фича — фиксированное досье и справочники по API (PubChem, DailyMed): семантический поиск не нужен.
  • Мониторинг трендов (более поздний этап) — главный потребитель семантического retrieval: поток статей, патентов, новостей.
  • Каталог стратегий — структурированные определения с выбором по правилам и метаданным.

Классифицированы 7 типов документов (нормативные руководства, лейблы, статьи, патенты, справочные базы, новости, частные документы) с назначением, правами и способом обработки. Единица хранения — не «чанк», а наблюдение с провенансом (источник, локатор, уровень доступа, версия). Векторный индекс отложен до этапа мониторинга — по отсутствию потребности, не по нехватке ресурсов.

Рабочее окружение и доступ к моделям

Репозиторий: github.com/WooperWise/absorbix-ai — uv-проект (Python 3.12) с Docker; проверочные скрипты, датасет, документация.
Локальная модель (рабочее решение): vLLM-сервер с Qwen3.8-27B-FP8 на GPU (64 ГБ) за OpenAI-совместимым API. Smoke-тест из окружения uv — 5/5 проверок; из Docker-контейнера — 5/5, включая structured output по JSON-схеме (извлечение трёх полей из русского текста с валидацией). Лог: material/part4/logs/check_local_model_2026-10-18.log (+ _docker.log).
Google AI Studio (неудачная попытка): ключ free tier получен и авторизуется, но Generative Language API отклоняет запросы из региона IP машины (Yandex Cloud, РФ): «User location is not supported». Лог: check_gemini_key_2026-10-18.log. Решение (прокси / Vertex AI / полный отказ) отложено; работа переведена на локальную модель.

Секреты и лимиты

  • Ключи — только в .env (в git и Docker-образ не попадают, проверено .gitignore/.dockerignore); в логи ключи не пишутся (маскируются).
  • Локальная модель — без квот и оплаты; ограничение одно: последовательная обработка на одной GPU.
  • Лимиты Gemini free tier проверить не удалось — API недоступен из региона (см. выше).
