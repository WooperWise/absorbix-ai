# Этап 6. Типы документов и хранилище для RAG

**Дата: 18 октября 2026 года.** Выполнение блока 6 задания этапа (`parts_desc/part1_week1.md`): классифицировать типы документов, описать формирование хранилища, обосновать применение RAG. Блок применён, поскольку платформа по ТЗ читает литературу, патенты и инструкции. Формат — проектный документ без кода: это зафиксированное решение, а не пробел (см. раздел 3).

## 1. Нужен ли RAG: ответ по компонентам платформы

Короткий ответ: семантический поиск по документам нужен **не везде**, а в конкретных частях системы. Там, где документ известен заранее, решают идентификаторы и API.

| Компонент платформы | Механизм доступа к знаниям | Семантический retrieval |
|---|---|---|
| Первая фича: профиль + диагностика ограничивающего фактора | Фиксированное досье кейса (`data/evidence/`, раздача по идентификаторам через `load_case`) + справочники по API (PubChem, DailyMed) | не нужен |
| Каталог стратегий | Структурированные `StrategyDefinition` (этап 3), выбор правилами и метаданными | позже, для «похожих стратегий» |
| Мониторинг трендов (этап 7 ТЗ) | Поток статей, патентов, новостей: дедупликация, классификация, поиск по теме | **да — главный потребитель** |
| Объяснимость и ссылки | Доступ по `source_id` к наблюдениям и карточкам | не нужен (lookup) |
| Частные документы партнёров | Импорт по правам в изолированный workspace | да, при росте корпуса |

**Вывод:** строить векторный индекс сейчас — решать задачу, которой на этой стадии нет. Первую фичу закрывает досье-режим датасета этапа 5; векторный поиск откладывается до этапа мониторинга трендов.

## 2. Классификация типов документов

| Тип | Примеры | Зачем платформе | Доступ и формат | Способ обработки |
|---|---|---|---|---|
| Нормативные руководства | FDA guidances, ICH quality guidelines | Регуляторные рамки, границы выводов | Веб, публично; версии фиксируются | Карточки-парафразы с `locator` |
| Инструкции и лейблы | DailyMed (США), ГРЛС (РФ) | Фактический состав, форма, влияние пищи, предупреждения | DailyMed REST API v2 (JSON, проверен); ГРЛС — веб без проверенного API | API-извлечение + карточки |
| Научные статьи и рефераты | PubMed / Europe PMC | Доказательная база стратегий | Europe PMC REST (проверен живым запросом); полные тексты — по правам | Извлечение по схеме с `origin_kind` |
| Патенты и Orange Book | Патентные базы, Orange Book | Защита, окна дженериков | Веб/файлы, публично | Справочные поля, версионирование |
| Справочные базы | PubChem, ChEMBL, FDA IIG | Свойства молекул, допустимые количества эксципиентов | PubChem PUG REST (проверен живым запросом) | **API, не RAG-корпус** |
| Новости и тренды | Отраслевые источники | Мониторинг | RSS/скрейпинг; права различаются | Этап 7 |
| Частные документы партнёров | Досье брендов, протоколы | Реальные кейсы | По соглашению, конфиденциально | Workspace-изоляция этапа 3 |

## 3. Формирование хранилища (проектное описание)

**Единица хранения** — не «чанк векторной базы», а наблюдение/карточка с провенансом: `source_id`, URL, `locator`, `access_level`, дата/версия, ограничения применимости. Ровно так устроены `data/evidence/cards/` и контракт `observation` этапа 3.

**Конвейер:** документ → извлечение (LLM с жёсткой схемой, ограниченная роль) → программная проверка (schema + предметные правила) → наблюдение с `origin_kind` → реестр/индекс. Отказ на любом шаге — явный статус, а не молчаливое угадывание.

**Границы доступа:** `workspace_id` (этап 3); правило датасета — `reference/`, `examples/`, `qa/` никогда не попадают в контекст агента; частные документы — отдельные области поиска и индексов.

**Векторный индекс — отложен** до этапа мониторинга трендов. Честные причины: (1) текущий корпус мал — 24 карточки и реестры, раздача по идентификаторам полностью решает задачу; (2) досье первой фичи фиксировано; (3) семантический поиск даёт пользу при постоянном потоке новых документов, которого пока нет. Формулировка «не хватает GPU» была бы неточной: эмбеддинги считаются и на CPU — дело в отсутствии потребности, а не в ресурсах.

## 4. Обоснование применения RAG

- **ТЗ** (`DESCR.md`): LLM без обвязки путают свойства молекул и придумывают исследования; каждый вывод требует ссылку на источник и оценку доказательности. Свободная генерация несовместима с продуктом — знание поставляется извне, с провенансом.
- **Этап 2**: LLM без инструментов зафиксирована как слабая базовая линия; архитектуры типа ChemCrow показывают пользу связки «модель + инструменты + источники».
- **Этап 3**: контур проверяемых наблюдений (`origin_kind`, верификация цитат, LLM-шлюз с политиками) уже спроектирован — RAG наполняет его, а не вводится модой.
- **Этап 5**: фиксированное досье — управляемая форма подачи контекста; датасет прямо проверяет, что система не подменяет источники и не игнорирует ограничения.

**Отличие от классического RAG:** не «топ-к чанков в промпт», а извлечение по схеме → проверка → наблюдение с границами доступа. Классическая схема уязвима к подмене обоснования нерелевантным фрагментом; контракт этапа 3 это запрещает структурно.
