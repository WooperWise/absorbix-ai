## Рабочее окружение и доступ к моделям

### Хронология подключения

1. **Google AI Studio (попытка).** Ключ free tier получен, сохранён в `.env` (gitignored). Скрипт `scripts/check_gemini_key.py` подтвердил авторизацию ключа, но API отклонил запросы: `400 FAILED_PRECONDITION — User location is not supported for the API use` — блокировка Generative Language API по региону IP машины (внешний адрес — диапазон Yandex Cloud, РФ). Лог: [`logs/check_gemini_key_2026-10-18.log`](logs/check_gemini_key_2026-10-18.log).
2. **Локальная модель (рабочее решение).** На рабочей станции уже развёрнут vLLM-сервер с моделью **Qwen3.8-27B-FP8** (GPU NVIDIA CMP 170HX, 64 ГБ VRAM), OpenAI-совместимый API `http://localhost:8000/v1`. Проверено скриптом `scripts/check_local_model.py` из окружения uv и из Docker-контейнера — оба прогона 5/5.

### Почему локально — Qwen через vLLM

Семейство Qwen стабильно входит в число наиболее используемых открытых моделей 2026 года в обзорах и рейтингах применения (OpenRouter Rankings — https://openrouter.ai/models; обзор top open-weight LLM 2026 — https://agyn.io/blog/top-open-weight-llms-2026), а де-факто стандартом доступа к само-хостингу LLM является OpenAI-совместимый API, который реализует vLLM (документация — https://docs.vllm.ai/en/latest/serving/openai_compatible_server.html). Эти ссылки подтверждают распространённость подхода, а не превосходство конкретной модели над альтернативами: выбор Qwen3.8-27B-FP8 продиктован тем, что сервер уже развёрнут на этой машине для предыдущего проекта, и он проходил отборочное тестирование.

## Инфраструктурные тесты (пункт 4 задания)

Скрипты в `scripts/`, каждый завершается кодом 0/1 и пишет лог в `material/part4/logs/`:

- `check_gemini_key.py` — валидация ключа, `listModels`, `generateContent`, structured output (`response_schema`). Итог: 2/3 — заблокировано регионом.
- `check_local_model.py` — `GET /v1/models`, `chat.completions`, structured output (`response_format: json_schema`). Итог: **5/5 из uv** ([`logs/check_local_model_2026-10-18.log`](logs/check_local_model_2026-10-18.log)) и **5/5 из Docker** ([`logs/check_local_model_2026-10-18_docker.log`](logs/check_local_model_2026-10-18_docker.log)).

Structured output — не просто вызов: модель извлекла из русского текста об итраконазоле три поля по Pydantic-схеме (`compound` / `limiting_factor` / `proposed_strategy`) и ответ прошёл валидацию. Это ровно паттерн «LLM-извлечение + программная проверка схемы» из архитектуры этапа 3 (раздел 2.10). Это инфраструктурная проверка схемы, а не научная проверка качества извлечения.

## Воспроизведение

```bash
uv sync                                   # окружение
uv run scripts/check_local_model.py       # локальная проверка
docker compose build && docker compose run --rm check   # контейнерная проверка (host-сеть к vLLM)
```

Структура репозитория после этапа: корневой uv-проект (`src/` — код будущего приложения плоско, `scripts/` — вспомогательные прогоны), `Dockerfile`/`docker-compose.yml`, `material/` — отчёты этапов, `.env` вне git.

## Ограничения и нерешённое

- Gemini API недоступен с текущего региона IP. Решение (прокси или Vertex AI) — не в этом дедлайне; ключ сохранён.
- Тесты — инфраструктурные smoke-проверки на одном тексте; качество извлечения по-настоящему оценится на данных этапа 5.
- `opencode.json` в корне унаследован от предыдущего проекта (указывает на vLLM-провайдер) — примечание для чистки, не влияет на работу.
