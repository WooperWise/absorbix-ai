# Этап 7. Первая фича: детальное описание

**Дата: 18 октября 2026 года.** Выполнение блока 7 задания этапа (`parts_desc/part1_week1.md`): детальное описание первой фичи, её видение и обоснование выбора. Это **проектный документ, код не написан** — реализация планируется следующим этапом; задание блока 7 требует описание, а не работающий код.

## 1. Что строим

**Вертикальный срез платформы**: исследовательский кейс → профиль препарата → диагностика ограничивающего фактора всасывания → не более трёх обоснованных кандидатов стратегий → структурированный ответ по контракту `benchmark_response`.

Входом служит кейс датасета этапа 5 (`data/`, dev-сплит): постановка задачи пользователя, зафиксированная ревизия кейса (намерение, путь введения, требования) и фиксированное досье — карточки источников с провенансом. Выходом — JSON, проходящий схему `data/schemas/benchmark_response.schema.json`: статус решения, утверждения со ссылками на факты досье, предупреждения, недостающие входы, кандидаты с обоснованием и следующей проверкой.

Ключевая способность, которая отличает фичу от «генератора советов»: **умение отказываться**. Неполное досье → `needs_clarification` с перечнем недостающего; запрос вне рамок → `out_of_scope`; невозможность обосновать кандидата фактами → кандидат не выдаётся. В датасете специально есть такие варианты кейсов, и правильный отказ там ценнее уверенной выдумки.

## 2. Видение

Фича адресует главный рабочий вопрос технолога: **какие варианты изменения препарата разумно проверить экспериментально, на основании каких данных и при каких ограничениях**. Не «список способов повысить растворимость», а проверяемое предэкспериментальное решение: каждый вывод опирается на факт досье с указанием источника, каждая гипотеза помечена как гипотеза, каждое численное обещание отсутствует до появления расчётной модели.

Пользователь получает не замену эксперимента, а экономику эксперимента: с чего начать проверку и что уже известно. Диалоговое уточнение вместо угадывания: если данных мало, система спрашивает, а не додумывает.

## 3. Почему именно она и почему первой

1. **Ядро ценности из ТЗ.** Профиль и диагностика ограничивающего фактора — первые пункты пользовательского сценария ТЗ (`DESCR.md`); без них стратегии selection повисает в воздухе.
2. **Центр архитектуры этапа 3.** Фича реализует модули M06 (воспроизводимый расчётный профиль) и M07 (объяснимая оценка ограничивающих факторов) на готовых наблюдениях M04 и с выходом в кандидатов в духе M08.
3. **Проверяемость без новой разметки.** Ответы сравниваются формальным оценщиком датасета этапа 5 (`evaluate.py`, dev-сплит) — метрика существует до написания кода.
4. **Изоляция от внешних рисков.** Досье фиксировано, внешние API не нужны: сетевые ограничения среды (подтверждённые этапами 4–6) не блокируют разработку.

## 4. Архитектура фичи

### 4.1 Шаги

```
кейс (data/pipeline, dev-сплит)
  → 1. адаптер кейса: сборка модельно-видимого досье      [детерминированно]
  → 2. роутер варианта: готов / неполный / вне рамок       [детерминированно]
  → 3. извлечение фактов из карточек по схеме               [LLM + жёсткая схема]
  → 4. проверка ссылок: fact_refs только существующие       [детерминированно]
  → 5. профиль + диагноз ограничивающего фактора            [правила; LLM формулирует]
  → 6. кандидаты ≤3 с опорой на факты                       [LLM + схема]
  → 7. сборка и валидация ответа по JSON-схеме              [детерминированно]
```

Шаги 2 и 4 — защитные контуры: роутер ловит кейсы-отказы до генерации, валидатор ссылок не пропускает выдуманные `fact_refs` (невалидная ссылка — повторный запрос, затем отбрасывание утверждения).

### 4.2 Компоненты (проектируемые, `src/`)

| Компонент | Ответственность | Тип |
|---|---|---|
| `case_loader` | Кейс + досье из `data/` (по образцу `load_case.py` пакета: карточки, наблюдения, сущности, метаданные источников) | код |
| `case_router` | Классификация варианта кейса; выбор пути: полный / уточнение / отказ | код |
| `extraction` | Извлечение фактов и ограничений из карточек по Pydantic-схеме | LLM |
| `diagnosis` | Диагноз ограничивающего фактора: правила по четырём классам ТЗ (растворимость, проницаемость, стабильность, метаболизм первого прохождения); LLM формулирует объяснение и помечает нехватку правил — в `warnings`, не выдумывая | гибрид |
| `candidates` | Генерация ≤3 кандидатов; `source_fact_refs` обязательны, без опоры — статус `conditional`/`rejected` | LLM + код |
| `response` | Сборка `benchmark_response`, jsonschema-валидация | код |

### 4.3 Данные: вход и выход

**Вход** (из `data/`): `pipeline/inputs` (кейс: намерение, путь, требования, текст задачи, ссылки досье), `evidence/cards` (карточки-парафразы с `source_id`, `locator`, SHA-256), `evidence/observations`, `evidence/entities`, `evidence/sources.json`. Только dev-кейсы; `reference/` и test-сплит в разработке не открываются (правило честной игры, `data/README.md`).

**Выход**: JSON по `benchmark_response_v1` — `decision_status`, `claims` (текст + `fact_refs` + `origin_kind`: факт источника / гипотеза / проектное предложение), `warnings`, `missing_inputs`, `actions`, `candidates` (≤3), `numeric_predictions` — **пусто**: расчётной модели нет, численный прогноз без неё контракт платформы запрещает.

### 4.4 Где работает модель

LLM (локальная Qwen3.8-27B-FP8 за OpenAI-совместимым API vLLM, проверена этапом 4) — только шаги 3 и 6 и формулирование объяснений шага 5, всегда со схемой structured output (подтверждено smoke-тестом этапа 4). Решения о статусе, диагнозе и допуске кандидатов принимает код. Модель не видит ничего кроме досье кейса; секреты в контекст не попадают.

## 5. Границы и ограничения

- Код не написан — документ является проектом; реализация и прогон на одном кейсе, затем на dev-сплите — следующий этап.
- Формальный оценщик проверяет структуру и ссылки, не научную истинность; содержательная оценка — экспертная приёмка (открытый пункт датасета).
- Диагноз правилами на 20 контекстах — управляемый overfit-риск: правила пишутся из предметной логики ТЗ, не под подсматривание кейсов; нехватка правил честно уходит в `warnings`.
- Полный путь пользователя (веб-поиск, PDF-разбор, чат) не входит в первую фичу — рамка зафиксирована датасетом: фиксированное досье.
